# 🔐 Security Audit

**القاعدة:** كل حكم يجي من ملف موجود (`file:line`) أو من استعلام على الداتابيس الحية. ممنوع الجواب من «أفضل الممارسات». ممنوع تضيف مكتبة أو خدمة عشان تقدر تفحص. **لا تعدّل أي كود بالمرحلة 1–3.**

## 🔧 أدوات (شغّلها أول)
- `bash .claude/skills/security-audit/scripts/secrets.sh <repo>` — يمسح الريبو **وكل تاريخ git** عن مفاتيح، يفك كل JWT ويطلع `role` حقه (anon عادي / service_role كارثة)، ويتأكد إن ملفات `.env` والمفاتيح بـ `.gitignore`.
- لو المشروع على Supabase: شغّل استعلامات `references/supabase.sql` عن طريق `execute_sql`، و`get_advisors(type=security)`، و`list_edge_functions` (شيّك `verify_jwt`). **الداتابيس الحية هي الحَكَم، مو ملف schema بالريبو.**

## المرحلة 1 — «وش لقيت» (قائمة قصيرة، اكتب «مو موجود» لأي شي ناقص)
- اللغة، الفريمورك، النسخة.
- هل فيه كود يشتغل بجهة موثوقة (API routes، server actions، edge/serverless functions، باك إند منفصل، دوال SECURITY DEFINER) ولا كل شي ينزل للمتصفح؟
- وين البيانات (DB مستضافة، BaaS، ORM، ملفات، تخزين المتصفح، ولا شي).
- كيف ينعرف المستخدم (مزوّد auth، sessions يدوية، API keys، ولا شي).
- كيف ينشر، ومن وين تجي متغيرات البيئة.

## المرحلة 2 — احكم على كل بند بوحدة من 4
**APPLIES** (موجود: الحكم + `file:line`) · **MISSING** (لازم يكون وما هو: وش تضيف) · **N/A** (ما فيه هالسطح: سطر ليش) · **CANNOT VERIFY** (وش تحتاج تشوف).

1. **الأسرار.** كل مفتاح/توكن/باسورد/connection string/private key بالكود أو الإعدادات أو env مرفوع. السؤال الوحيد: **هل يوصل للي يحمّله المتصفح؟** احكم من قواعد البناء حق هالمشروع (أي أسماء عامة: `VITE_`، `NEXT_PUBLIC_`، ملف config ينزل كما هو) مو من العرف. لكل سر يوصل للمتصفح: وش يقدر يسوي لو انسرق، وبديله بهالستاك. شيّك التاريخ و`.gitignore`. لو ما فيه جهة موثوقة أبد: قلها صريح «كل مفتاح بهالمشروع عام».
2. **القيم اللي يرسلها المتصفح** وتقرر شي: أسعار، مجاميع، كميات، أدوار، باقة، كود خصم، id يحدد أي سجل ينقرا/ينكتب، أي شي مثل `isAdmin`، **وحدود (limit) تنمرر لدالة**. لكل وحدة: الجهة الموثوقة تعيد حسابها/تتحقق، ولا تاخذها كما هي؟ أي فحص بالمتصفح (زر معطّل، validator، schema) = واجهة مو حماية.
3. **مين يحق له الطلب.** لكل نقطة تقرا أو تكتب بيانات: تتطلب هوية موثّقة؟ وين ينفحص؟ علّم أي وحدة ترجع/تغيّر بيانات مستخدم بدون فحص، أو تعتمد على إن الواجهة تخفيها (redirect، زر مخفي). نقطة وحدة تغطي الكل ولا الفحص مكرر بكل handler؟ وأي endpoint ياخذ `user_id` من الطلب بدل ما يطلعه من الـ session؟
4. **وش تفرض قاعدة البيانات نفسها.** فيه قواعد per-row (RLS/Firestore rules)؟ شغّالة؟ فيه وحدة فعلياً «allow anyone» (`using (true)`)؟ لو المتصفح يوصل للداتابيس مباشرة بمفتاح نازل معاه → فلترة الكود ما لها قيمة، والقواعد هي الحماية الوحيدة.
5. **وش يوقف التكرار.** كل نقطة توصلها بدون دخول، وكل وحدة تكلّف فلوس/وقت لكل طلب (API مدفوع، إيميل/SMS، ميديا، موديل AI، حساب ثقيل). لكل وحدة: فيه حد per IP / per user / per key؟ وين ينفرض؟ وش يصير لو تعدّاه؟ ضمّنها: login، signup، reset password، OTP. لو ما فيه حد: كم يقدر واحد يصرف بساعة، ووين مكان الحد بهالستاك.

## ⚠️ فخاخ Supabase (تحقق منها دايماً)
- **سياستين permissive على نفس الجدول تنجمع بـ OR.** سياسة شرط إضافي (مثل MFA) لازم تكون `AS RESTRICTIVE`، وإلا أي مستخدم يقرا بيانات الكل. شيّك `pg_policy.polpermissive`.
- **RLS شغّال وبدون سياسات** = مقفول على المتصفح (صح لجداول داخلية). الـ advisor يطلعه INFO مو ثغرة.
- **دالة SECURITY DEFINER** يقدر `anon`/`authenticated` يشغّلها = تتجاوز RLS. لكل وحدة: تشتق المستخدم من `auth.uid()`؟ تاخذ `uid` أو `lim` من المستدعي؟ عندها حد؟ لازم `set search_path`.
- **Edge Function:** `verify_jwt: true` + `auth.getUser()` قبل أي شي يكلّف؛ `service_role` من `Deno.env` بس.
- **مفتاح anon بالتطبيق عادي** — بشرط إن كل جدول عليه RLS.
- **حدود Auth** (signup/login/OTP/reset) بالداشبورد: Auth → Rate Limits. ما تنقرا بـ SQL → CANNOT VERIFY واطلب سكرين شوت.

## المرحلة 3 — التقرير
جدول وحد: **البند · الحالة · الدليل (file:line) · وش يصير لو انترك · الإصلاح بهالستاك**. بعده رتّب الكل: **قابل للاستغلال الحين / ضعيف / سليم / يحتاجك**. لا تعدّل شي. احفظ التقرير بـ `docs/company/SECURITY-AUDIT-<project>-<date>.md` لو المشروع فيه `docs/company`.

## المرحلة 4 — الإصلاح (بعد موافقة المستخدم بس)
- بند واحد كل مرة، **الأصغر أول**، وبأنماط موجودة بالمشروع (migration بنفس أسلوب الموجودة، نفس طريقة الـ rate limit المستخدمة).
- لو تحتاج مكتبة/خدمة جديدة فعلاً: قل وش وليش **قبل**.
- كل إصلاح: test يمنعه يرجع (نفس أسلوب `bug-hunter`)، شغّل الاختبارات، وأعد الاستعلام اللي كشف المشكلة وأثبت إنها انحلت.
- تعديل كبير (auth، schema، دفع) يمر على `diwaniya-company` أول.
